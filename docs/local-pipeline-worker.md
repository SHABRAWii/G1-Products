# Local GPU pipeline worker

The dashboard sends real pre-training work to a separate worker process. The worker uses a disposable directory per stage, stores its outputs in MinIO, and records each artifact in PostgreSQL.

## Stages implemented

- Pose extraction: source video → PromptHMR → `smplx.npz`; stores the direct PromptHMR `results.pkl` evidence.
- Robot retargeting: reviewed SMPL-X → GMR → safe Unitree G1 29-DoF `robot_motion.npz`.
- Visualization: GMR robot motion → official G1 mesh transforms → interactive digital twin + matching headless MP4 evidence.
- Training: safe G1 motion NPZ → mjlab CSV/NPZ conversion → unitree_rl_mjlab motion-imitation training → policy checkpoint (`.pt`, plus `policy.onnx` when exported). Success atomically records the immutable `TrainingRecipe`, `TrainingRun`, candidate `Policy`, and `PolicyVersion`.

The visualization MP4 is not generated by a second 3D engine. The worker opens
the private `/render/digital-twin` capture surface in headless Chrome, commands
the production Three.js viewer at exact media times, and pipes its 1920×1080
frames to FFmpeg. Consequently the downloadable evidence uses the same mesh,
camera, floor/grid, fog, lights, materials, interpolation, and tone mapping as
the interactive viewer.

## Required model environments

Each model root below is validated independently — a worker only needs the roots/envs for the stages it actually serves. A training-only worker, for example, only needs `ROBOMOTION_TRAIN_ROOT`/`ROBOMOTION_TRAIN_ENV`; it does not need PromptHMR or GMR installed to report itself ready.

Set these values in the terminal that starts the worker:

```bash
export ROBOMOTION_PROMPTHMR_ROOT=/path/to/PromptHMR
export ROBOMOTION_GMR_ROOT=/path/to/GMR
export ROBOMOTION_TRAIN_ROOT=/path/to/unitree_rl_mjlab
export ROBOMOTION_PROMPTHMR_ENV=phmr
export ROBOMOTION_GMR_ENV=gmr
export ROBOMOTION_TRAIN_ENV=unitree_rl_mjlab
# Optional local alternative to a Conda environment:
# export ROBOMOTION_TRAIN_PYTHON=/path/to/unitree_rl_mjlab/.venv/bin/python
export DATABASE_URL='postgresql://robomotion:robomotion@localhost:5432/robomotion?schema=public'
export OBJECT_STORAGE_ENDPOINT=http://localhost:9000
export OBJECT_STORAGE_BUCKET=robomotion
export OBJECT_STORAGE_ACCESS_KEY=robomotion
export OBJECT_STORAGE_SECRET_KEY=robomotion-local-secret
export ROBOMOTION_DASHBOARD_URL=http://127.0.0.1:3000
# Only needed when Chrome is not installed in a standard location:
# export ROBOMOTION_CHROME_BIN=/path/to/google-chrome
npm run worker:motion
# In a second terminal or on a separately assigned GPU:
npm run worker:training
```

`npm run worker` is an alias for `npm run worker:motion`. Training must be
started explicitly with `npm run worker:training`. Local and production
workers therefore have separate heartbeats, so a missing training runtime or a
multi-hour training process cannot block pose extraction or retargeting.

The motion/training boundary is
`motion.robot.unitree-g1-29dof-npz/v2`. It uses numeric NPZ arrays plus JSON
metadata and is always loaded with `allow_pickle=False`. Legacy Python pickle
motion files are rejected before execution.

The dashboard must be running and reachable through
`ROBOMOTION_DASHBOARD_URL`. Google Chrome/Chromium and FFmpeg must be installed
on the worker. The canonical GPU-worker image installs both automatically.

PromptHMR and GMR are direct upstream installations. Their source trees and model weights must be installed in their respective Conda environments. PromptHMR has a non-commercial research-use license; verify the intended deployment is permitted before using it beyond that scope.

The dashboard worker and adapters are RoboMotion code. They import the installed model packages directly and do not copy model code into this repository.
